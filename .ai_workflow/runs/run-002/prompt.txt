为什么没有脱离 01_design.md：
No-Change Resource Closure 是 Resource Engine 确定性数值底座的闭环补强，服务于章节生成层、审稿增强层和发布优化层。5.7B-2 延续 5.7B-1 的盘点结论，把“无资源变化但已闭合”和“资源检查缺失”的语义边界落实到程序类型、报告字段和最小测试中，不修改总体设计，不直接修复业务输出。

背景：
5.7B-1 盘点报告已确认：
- 有 Resource Plan 且为 no-change 模式时，零事件章节通常能 PASS 且不阻断；
- 无 Resource Plan 时，报告缺少明确 closure 语义，无法稳定区分“无资源变化”和“检查缺失”；
- `no_resource_change` plan 下如果正文出现资源事件，目前语义不够明确；
- 当前报告缺少稳定的 `closureStatus` 字段供后续 publish-ready、continuity、review、export 消费。

本轮核心目标：
在最小范围内定义并实现 no-change resource closure 判定语义。目标是让程序和报告能够明确区分：
- `no_change_closed`：已检查，确认无资源变化；
- `normal_closed`：有资源事件且资源计算闭合；
- `not_checked`：缺少必要检查或缺少 Resource Plan，不能当作 no-change closure；
- `resource_failed`：资源计算失败、阻断或存在真实资源异常。

本轮不是 publish-ready 全量接入任务，也不是业务输出修复任务。

实现要求：
1. 定义稳定的 closure 语义，优先使用 `closureStatus` 或等价字段。
2. `no_change_closed` 必须只表示“已执行检查，且确认无资源变化已闭合”。
3. `not_checked` 必须与 `no_change_closed` 区分，不能把缺失 Resource Plan 的情况静默当作已闭合。
4. 正常资源变化闭合应保留现有 PASS 行为，并能标记为 `normal_closed` 或等价语义。
5. 真实资源异常仍必须保持 FAILED / WARN / blocking 语义，不能为了 no-change 放宽失败条件。
6. 不允许 LLM 临时补写收益、消耗或余额声明。
7. 不直接修改章节正文或业务报告来伪造验收通过。

建议最小实现方向：
- 在 Resource Plan final validation 或 Resource Consistency pipeline result 中补充明确的检查状态字段。
- 在 resource consistency report JSON/MD 中输出 closure 语义。
- 保持 no-change 章节不触发错误 BLOCKED / WARN。
- 对 `no_resource_change` plan 下出现资源事件的情况，至少在报告中给出清晰语义；是否升级 WARN 如有风险请在报告中说明。

代码级测试：
本轮需要补充或更新聚焦测试。建议至少覆盖：
- no-change 章节：有 no_resource_change plan、零事件、零 issue，应输出 `no_change_closed`，status PASS，blocking false；
- 缺失检查：无 Resource Plan 且零事件，不能输出 `no_change_closed`，应输出 `not_checked` 或等价语义；
- 正常资源变化：有资源事件且计算闭合，应输出 `normal_closed` 或等价语义，保持 PASS；
- 真实资源异常：仍应 FAILED / WARN / blocking，不得被 no-change closure 误放行；
- `no_resource_change` plan 下出现资源事件：必须有可审计语义，不能静默伪装成 no-change closure。
