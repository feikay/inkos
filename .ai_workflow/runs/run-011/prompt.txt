项目名称：inkos 小说生成项目

当前阶段：inkos 2.0：故事性大升级

当前任务：任务五点八：Book-level Resource Schema 与章节阶段化 Resource Plan

当前子任务：5.8A：盘点全局默认资源、章节阶段识别、fallback 分派、publish-ready 资源门禁，并提出抽象修复方案

Design Anchor：
- `.ai_workflow/01_design.md` 的“章节生成层”：资源变化必须由 Resource Engine 或明确 closure 语义支撑，LLM 不得临时发明收益、消耗或余额。
- `.ai_workflow/01_design.md` 的“审稿增强层”：资源未闭合不得 ready-for-review；no-change 章节必须区分“无变化已闭合”和“检查缺失”。
- `.ai_workflow/01_design.md` 的“发布优化层”：发布前必须汇总资源闭合状态，不得用导出或润色掩盖系统性缺陷。
- `.ai_workflow/01_design.md` 的“Resource Engine 与故事性升级的关系”：Resource Engine 是系统流小说的确定性数值底座，防止数值污染、资源闭合失败、LLM 乱编收益/消耗。
- `.ai_workflow/01_design.md` 的“No-Change Resource Closure 的设计目标”：区分没有资源变化与资源检查缺失，对无资源变化章节输出明确 closure 结论。

当前任务对应 `02_todo.md`：
- `5.8A：盘点 Resource Schema / Resource Plan mode / fallback / publish-ready 资源门禁`

当前任务为什么没有脱离 `01_design.md`：
本轮不是修某本书、某个章节或某个资源名，而是把真实验证暴露的问题抽象为 Resource Engine 的通用规则：book-level resource schema、章节阶段化 Resource Plan、schema/mode gated fallback、publish-ready 资源硬门禁。它仍属于章节生成层、审稿增强层和发布优化层的资源一致性底座。

背景：
真实新书验证暴露出一类系统问题：Resource Engine 可能把普通金钱/数字表达纳入强资源账本；Resource Plan 对系统/能力首次出现章节缺少通用阶段 mode；fallback recovery 可能选择与当前资源 schema 不匹配的策略；publish-ready 可能没有把 Resource Engine blocking / state-degraded / closureStatus=resource_failed 作为发布硬阻断。

重要原则：
- 不允许把修复写成某本书、某个资源名、某个章节的特例。
- 真实样本只是 evidence，修复必须抽象为程序规则、数据结构、prompt 约束或流程门禁。
- 不能直接编辑业务验证输出让结果通过。
- 常规研发循环不得修改 `.ai_workflow/01_design.md`。

本轮核心目标：
1. 盘点 Resource Engine 当前资源 schema 来源，确认是否存在全局默认资源污染。
2. 盘点普通数字/金额/价格/订单金额如何进入强账本，区分“资源账本数字”和“普通剧情数字”。
3. 盘点 Resource Plan 当前 mode，确认是否缺少通用 `system_bootstrap` / `resource_rule_reveal` 类章节阶段。
4. 盘点 fallback recovery 选择逻辑，确认 `defer_exchange` 等策略是否按 resource schema 与 plan mode gated。
5. 盘点 publish-ready / write-publish-export 是否读取 resource consistency report / chapter index status，并在资源未闭合时硬阻断。
6. 提出下一轮最小抽象实现方案与测试计划。
